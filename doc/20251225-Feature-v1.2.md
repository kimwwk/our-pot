## Feature 7: Database Backup & Restore

**Dependencies:** Feature 5 (manual tracking works)

**SAD References:**
- Section 3.6 (Backup & Export)

**Rationale:**
Enable users to backup and restore their entire financial database. Critical for disaster recovery, device migration, and data sovereignty. Simple, reliable, and implementable in v1.2.

**Security Model:**
- Unencrypted SQLite database file
- Relies on device security (lock screen, Android encryption-at-rest)
- Relies on cloud storage provider security (Google Drive, Dropbox)
- User can add encryption at file system/cloud level if desired
- Honest about security model (no false promises)
- Encryption can be added properly in v2 with user-controlled passwords

### 7.1 Implementation Tasks

#### 7.1.1 Database Backup Exporter
- [ ] Create `lib/data/export/db-backup-exporter.ts`:
  - Export `exportDatabase(db: SQLiteDBConnection): Promise<Uint8Array>`
    - Use Capacitor SQLite plugin's export functionality
    - Get raw database file bytes from SQLite connection
    - Use `db.exportToJson()` then convert to binary, OR
    - Use native file access to copy .db file
    - Return database bytes as Uint8Array
  - Export `createBackupFilename(): string`
    - Format: `ourpot-backup-YYYYMMDD-HHMMSS.db`
    - Use current timestamp for uniqueness
  - Export `getDatabaseSize(db: SQLiteDBConnection): Promise<number>`
    - Query database size for UI feedback
    - Return size in bytes

#### 7.1.2 Database Import/Restore
- [ ] Create `lib/data/import/db-backup-importer.ts`:
  - Export `validateBackupFile(fileData: Uint8Array): Promise<boolean>`
    - Check SQLite file signature (first 16 bytes = "SQLite format 3\0")
    - Attempt to open database connection (read-only)
    - Verify required tables exist (accounts, transactions, members, categories, changesets, change_requests)
    - Check schema version matches current version
    - Return true if valid, throw descriptive error if invalid
  - Export `importDatabase(fileData: Uint8Array): Promise<void>`
    - Close current database connection
    - Backup current database to temp location (safety net)
    - Write imported database to app's database location
    - Reopen database connection
    - Verify data integrity (transaction count > 0 or tables exist)
    - If failure, restore from temp backup
    - Delete temp backup on success
  - Export `getBackupMetadata(fileData: Uint8Array): Promise<BackupMetadata>`
    - Open database (read-only)
    - Query: transaction count, account count, member count, date range
    - Return metadata for UI display before import
    - Type: `{ transactionCount: number, accountCount: number, memberCount: number, oldestTransaction: string, newestTransaction: string, databaseSize: number }`

### 7.2 Data Safety & Error Handling

**Backup Safety:**
- ✅ Read-only operation (no risk to current database)
- ✅ Verify database connection before export
- ✅ Handle export errors gracefully (disk full, permission denied)
- ✅ Store last backup timestamp in localStorage

**Restore Safety:**
- ✅ Create automatic backup before restore (safety net)
- ✅ Validate file format before attempting restore
- ✅ Atomic operation (all-or-nothing)
- ✅ Restore from temp backup if restore fails
- ✅ Clear all app caches/contexts after restore
- ✅ Handle edge cases:
  - File corrupted mid-transfer
  - Insufficient disk space
  - Schema version mismatch (old backup on new app version)
  - User cancels file picker

**Edge Case: Schema Migrations**
- If backup schema version < current app schema version:
  - Attempt to run migrations on imported database
  - If migrations fail, reject import with clear error
  - Suggest user update app before creating backup
- If backup schema version > current app schema version:
  - Reject import (future app version backup)
  - Error: "This backup was created with a newer version of OurPot. Please update the app."

### 7.3 Testing Approach

**Done When:**
- ✅ Backup file can be created and shared (both native and web)
- ✅ Backup file can be imported successfully (both native and web)
- ✅ Current data is preserved during backup
- ✅ All data is restored correctly after import
- ✅ Invalid files are rejected with clear errors
- ✅ App restarts properly after restore (native: exit, web: reload)
- ✅ Large databases (10MB+) backup/restore successfully
- ✅ Platform detection works correctly (native vs web)
- ✅ Web fallbacks work in development mode (`npm run dev`)
- ✅ Cross-platform compatibility (backup on web, restore on native and vice versa)

**Tests:**

#### Functional Tests (Backup)
- **Export Success:** Create 5 transactions → backup → verify .db file created with correct filename format
- **File Size:** Backup database with 100 transactions → verify file size reasonable (< 1MB for typical data)
- **Share Sheet:** Create backup → tap share → verify Android share options appear (Drive, Email, etc.)
- **Multiple Backups:** Create backup twice → verify unique filenames (timestamps differ)
- **Empty Database:** Backup with no transactions → verify backup succeeds (schema still valid)
- **Large Database:** Create 10,000 transactions → verify backup completes in < 10 seconds

#### Functional Tests (Restore)
- **Round-Trip:** Create 3 transactions → backup → delete all data → restore → verify 3 transactions present
- **Metadata Preview:** Select backup file → verify preview shows correct transaction/account/member counts
- **Invalid File:** Select a .txt file → verify rejected with "Invalid database file" error
- **Corrupted File:** Create backup, modify bytes randomly → attempt restore → verify rejected with "Corrupted database" error
- **Schema Mismatch:** (Manual) Use backup from old app version → verify migration attempted or clear error shown
- **Disk Full:** (Simulated) Attempt restore with full disk → verify error handled gracefully, original data intact
- **Cancel File Picker:** Tap "Restore" → cancel file picker → verify no changes to database

#### Data Integrity Tests
- **Complete Restore:** Create 50 transactions with categories, members → backup → restore → verify:
  - All 50 transactions present
  - Categories match
  - Member associations correct
  - Amounts correct (cents preserved)
  - Dates correct
  - Soft-deleted records preserved
- **Account Settings:** Change currency, account name → backup → restore → verify settings preserved
- **ChangeSet History:** Approve 3 AI changesets → backup → restore → verify audit trail intact

#### Safety Tests
- **Temp Backup:** Simulate restore failure → verify original database restored from temp backup
- **Atomic Restore:** Kill app mid-restore → verify database in consistent state (either old or new, not corrupted)
- **Concurrent Access:** Attempt backup during active transaction → verify handled safely

#### UI/UX Tests
- **Backup Flow:** Complete backup flow → verify success toast, share sheet opens
- **Restore Warning:** Open restore sheet → verify warning banner visible and clear
- **Confirmation Checkbox:** Attempt restore without checking confirmation → verify button disabled
- **Loading States:** Backup/restore → verify loading spinners appear with descriptive text
- **Error Messages:** Test various error scenarios → verify user-friendly error messages (not raw exceptions)

#### Platform Compatibility Tests
- **Web Backup:** Run `npm run dev` → create backup → verify file downloads to browser Downloads folder
- **Web Restore:** Run `npm run dev` → restore backup → verify file picker opens, restore works, page refreshes
- **Native Backup:** Run on Android → create backup → verify Android share sheet opens with Drive/Email options
- **Native Restore:** Run on Android → restore backup → verify native file picker opens, app exits after restore
- **Cross-Platform Compatibility:** Create backup in browser → restore on Android → verify data intact
- **Cross-Platform Reverse:** Create backup on Android → restore in browser → verify data intact
- **Platform Detection:** Check `isNativePlatform()` → verify returns true on Android, false in browser
- **Web Share API:** Test on browser with Web Share support (Chrome Android) → verify share dialog appears
- **Web Share Fallback:** Test on browser without Web Share (desktop) → verify fallback message appears
- **Platform UI Text:** Verify UI shows correct text:
  - Native: "Share to Google Drive, Dropbox, or email"
  - Web: "File will download to your Downloads folder"
- **Restart Behavior:**
  - Native: Verify app exits after restore
  - Web: Verify page refreshes after restore
- **File Size Warning:** (Web) Attempt to backup/restore 150MB database → verify size warning appears

### 7.5 User Experience Flow

#### Backup Flow - Native (Android App)
1. User taps "Backup Database" in Settings
2. BackupSheet modal opens showing current database info
3. User taps "Create Backup"
4. Loading spinner appears ("Creating backup...")
5. Success: "✅ Backup created: ourpot-backup-20251225-143022.db"
6. Android share sheet opens automatically
7. User selects destination (Drive, Email, etc.)
8. File shared successfully
9. Last backup timestamp stored

**Estimated Time:** 1-3 seconds for typical database (< 1MB)

#### Backup Flow - Web (Development)
1. User clicks "Backup Database" in Settings
2. BackupSheet modal opens showing current database info
3. Info text: "File will download to your Downloads folder"

5. Loading spinner appears ("Creating backup...")

7. File automatically downloads to browser's Downloads folder
8. Toast: "File downloaded to Downloads folder"
9. Last backup timestamp stored

**Estimated Time:** 1-3 seconds for typical database (< 1MB)
