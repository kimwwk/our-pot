## Feature 2: Database Schema & Migrations

**Dependencies:** Feature 1 (SQLite connection established)

**SAD References:**
- Section 3.3 (Database Schema Design - complete ER diagram and SQL)
- Section 3.5 (Migrations & Versioning Strategy)

**Tasks:**

### 2.1 Schema Implementation
- [ ] Create `lib/data/migrations/` directory
- [ ] Create `001_initial_schema.sql` with:
  - `accounts` table (id, name, currency, balance, createdAt, updatedAt, deletedAt)
  - `members` table (id, accountId, name, role, isKitty, avatarUrl, timestamps)
  - `transactions` table (id, accountId, memberId, categoryId, type, amount, merchant, description, date, timestamps)
  - `categories` table (id, accountId, name, icon, color, timestamps)
  - `changesets` table (id, status, source, title, description, toolCallId, proposedAt, reviewedAt, rejectionReason)
  - `change_requests` table (id, changesetId, operationType, entityType, entityId, currentData, proposedData, executionOrder, createdAt)
  - `schema_migrations` table (version, applied_at, description)
- [ ] Add all indexes from SAD 3.3 (idx_transactions_date, idx_transactions_accountId, etc.)
- [ ] Add unique constraints (unique_kitty_per_account, etc.)

### 2.2 Balance Management Triggers
- [ ] Create trigger `update_balance_on_insert` (see SAD 3.3)
- [ ] Create trigger `update_balance_on_update` (see SAD 3.3)
- [ ] Create trigger `update_balance_on_delete` (see SAD 3.3)
- [ ] Implement reconciliation function for balance recalculation

### 2.3 Migration System
- [ ] Create `lib/data/migrations/migrate.ts` with:
  - Version detection (read from schema_migrations table)
  - Migration execution (run pending migrations sequentially)
  - Idempotency checks (IF NOT EXISTS)
  - Error handling and rollback
- [ ] Run migration on app initialization (in SQLiteContext)

### 2.4 Seed Data
- [ ] Create default account on first run
- [ ] Create default "Kitty" member (isKitty=true)
- [ ] Seed 5-10 default categories (Groceries, Transport, Rent, Entertainment, etc.)

**Done When:**
- All tables exist in both native and WASM SQLite
- Balance triggers fire correctly on transaction insert/update/delete
- Migration system runs on app start
- Default account, kitty member, and categories are seeded

**Testing Approach:**
- **Type:** Technical verification
- **Method:** SQL queries in browser console + trigger testing
- **Tests:**
  - Query `SELECT name FROM sqlite_master WHERE type='table'` → verify all 7 tables exist
  - Insert test transaction → verify balance in accounts table updates automatically
  - Update transaction amount → verify balance recalculates
  - Soft delete transaction → verify balance reverses
  - Check schema_migrations table → verify version recorded

## Feature 3: Repository Layer (Data Access)

**Dependencies:** Feature 2 (database schema exists)

**SAD References:**
- Section 3.4 (Data Access Layer - Repository Pattern)
- All repository method signatures specified in SAD 3.4

**Tasks:**

### 3.1 Base Repository Pattern
- [ ] Create `lib/data/repositories/BaseRepository.ts` with:
  - Common error handling
  - Transaction boundary helpers (BEGIN/COMMIT/ROLLBACK)
  - Utility methods (executeQuery, executeSingle, executeNonQuery)

### 3.2 Entity Repositories
- [ ] Create `lib/data/repositories/AccountRepository.ts`:
  - `getAll()` - fetch all active accounts
  - `getById(id)` - fetch single account with balance
  - `create(account)` - insert new account
  - `update(id, changes)` - update account details
  - `softDelete(id)` - mark account as deleted
  - `reconcileBalance(id)` - recalculate balance from transactions

- [ ] Create `lib/data/repositories/MemberRepository.ts`:
  - `getAllByAccount(accountId)` - fetch all members for account
  - `getHumanMembersByAccount(accountId)` - fetch only human members (isKitty=false)
  - `getKittyMember(accountId)` - fetch the kitty member (isKitty=true)
  - `getById(id)` - fetch single member
  - `create(member)` - insert new member
  - `update(id, changes)` - update member details
  - `softDelete(id)` - mark member as deleted

- [ ] Create `lib/data/repositories/TransactionRepository.ts`:
  - `getAllByAccount(accountId, filters?)` - fetch with optional filters
  - `getById(id)` - fetch single transaction
  - `create(transaction)` - insert (triggers balance update)
  - `update(id, changes)` - update existing transaction
  - `softDelete(id)` - mark as deleted (reverses balance)
  - `search(accountId, query)` - full-text search on merchant/description

- [ ] Create `lib/data/repositories/CategoryRepository.ts`:
  - `getAllByAccount(accountId)` - fetch all active categories
  - `getById(id)` - fetch single category
  - `create(category)` - insert new category
  - `update(id, changes)` - update category
  - `softDelete(id)` - mark category as deleted

- [ ] Create `lib/data/repositories/ChangeSetRepository.ts`:
  - `create(changeset, changeRequests[])` - insert changeset with requests (atomic)
  - `getById(id)` - fetch changeset with change requests
  - `updateStatus(id, status, reviewedAt)` - mark as approved/rejected/building
  - `getByStatus(status)` - fetch changesets by status
  - `getApprovedByAccount(accountId, limit?)` - fetch approved for audit trail
  - `applyChangeSet(id)` - execute change requests atomically (see SAD 4.6)

### 3.3 React Hooks
- [ ] Create `lib/data/hooks/useTransactions.ts` - wraps TransactionRepository
- [ ] Create `lib/data/hooks/useCategories.ts` - wraps CategoryRepository
- [ ] Create `lib/data/hooks/useMembers.ts` - wraps MemberRepository
- [ ] Create `lib/data/hooks/useChangeSet.ts` - accesses ChangeSetContext

### 3.4 Account Context
- [ ] Create `lib/data/contexts/AccountContext.tsx`:
  - Current account ID state
  - Current account metadata (name, currency, balance)
  - `switchAccount(accountId)` method

**Done When:**
- All repositories implemented with full CRUD operations
- Can create/read/update/delete all entities via repository methods in browser console
- React hooks provide data to components
- Balance triggers fire when transactions are created/updated/deleted
- AccountContext provides current account to entire app

**Testing Approach:**
- **Type:** Technical verification + unit tests
- **Method:** Repository method calls in console, automated unit tests

  - Create transaction → verify balance updated automatically

## Feature 6: AI ChangeSet System (Core Differentiator)

**Dependencies:** Feature 5 (manual tracking works as baseline)

**v0 Prototype Reference:**
- `v0-our-pot-expense-tracker/components/ai-agent-panel.tsx` - AI chat interface
- `v0-our-pot-expense-tracker/components/changeset-widget.tsx` - Review widget UI
- `v0-our-pot-expense-tracker/components/agent-tab.tsx` - Agent tab layout

**SAD References:**
- Section 4 (Complete ChangeSet Domain Logic)
- Section 5 (AI & Agent Integration)
- Section 6.5 (Review Widget Pattern)

**Tasks:**

### 6.1 ChangeSet Context & Keyed Buffer
- [ ] Create `lib/data/contexts/ChangeSetContext.tsx` (see SAD 4.2):
  - Keyed buffer state (Map<string, ChangeRequest>)
  - Current changeset status (idle | building | pending_approval)
  - Changeset metadata (title, description)
  - `addChangeRequest(key, request)` - upsert to buffer
  - `removeChangeRequest(key)` - discard from buffer (action: "DISCARD")
  - `clearBuffer()` - reset
  - `transitionToPendingApproval()` - submit for review
  - `transitionToBuilding()` - rejection with feedback
- [ ] Add ChangeSetContext to root layout

### 6.2 Vercel AI SDK Setup
- [ ] Install Vercel AI SDK: `npm install ai`
- [ ] Configure OpenAI provider (user brings own API key)
- [ ] Create AI client wrapper in `lib/ai/client.ts`

### 6.3 System Prompt & Context
- [ ] Create `lib/ai/prompts.ts` with system prompt (see SAD 5.2):
  - Role definition (financial transaction assistant)
  - Key behaviors (amounts in pence, keyed buffer upsert, approval workflow)
  - Available tools summary
  - Iterative refinement instructions
- [ ] Implement context window management
- [ ] Add currency conversion guidance (decimal → cents)

### 6.4 AI Read Tools
- [ ] Create `lib/ai/tools/read-tools.ts` (see SAD 5.3):
  - `getCategories` - fetch all categories for current account (returns immediately)
  - `getMembers` - fetch all members for current account (returns immediately)
  - `searchTransactions` - search with filters (returns immediately)
- [ ] Implement immediate execution (call addToolOutput right away)

### 6.5 AI Proposal Tools
- [ ] Create `lib/ai/tools/proposal-tools.ts` (see SAD 5.3):
  - `createTransactionChangeRequest` - propose creating transaction
  - `updateTransactionChangeRequest` - propose updating transaction
  - `deleteTransactionChangeRequest` - propose deleting transaction
  - `createCategoryChangeRequest` - propose creating category
- [ ] Each tool adds to keyed buffer (NO immediate execution)
- [ ] Support `action: "DISCARD"` to remove from buffer
- [ ] Implement upsert logic (same entityId overwrites)

### 6.6 Amount Conversion & Validation
- [ ] Create `lib/ai/validation.ts` (see SAD 5.2):
  - `validateAndConvertAmount(decimal)` - converts 42.50 → 4200
  - Business rule validation (amount > 0, max 2 decimals, date not in future, etc.)
  - Schema validation with Zod
  - Return validation errors to AI for retry

### 6.7 Confirmation Tools
- [ ] Create `lib/ai/tools/confirmation-tools.ts`:
  - `confirmChangeSet(title, description)` - transitions to pending_approval
  - `resetChangeSet()` - clears buffer (rare)
- [ ] `confirmChangeSet` does NOT call addToolOutput immediately (pauses stream)

### 6.8 Review Widget
- [ ] Create `components/features/agent/ReviewWidget.tsx` (see SAD 6.5):
  - Listens for pending_approval status from ChangeSetContext
  - Renders dialog/sheet with all change requests
  - Shows before/after for updates (currentData vs proposedData)
  - Displays amounts in currency format (converts cents → display)
  - "Approve" button → executes changeset atomically
  - "Reject" button → returns to building state OR complete rejection
  - Feedback textarea for iterative correction
- [ ] Create `components/features/agent/ChangeRequestList.tsx` - renders individual change requests

### 6.9 Atomic Execution
- [ ] Implement atomic execution in ChangeSetRepository.applyChangeSet() (see SAD 4.6):
  - Wrap all operations in single DB transaction (BEGIN...COMMIT/ROLLBACK)
  - Execute change requests sequentially by executionOrder
  - If any operation fails, rollback entire transaction
  - Return execution results or error details
- [ ] Handle execution_failed state (feed error back to AI for auto-correction)

### 6.10 Stream Pause-Resume Pattern
- [ ] Implement pause-resume in ReviewWidget:
  - When confirmChangeSet called, do NOT call addToolOutput
  - User reviews in dialog
  - On approve: call addToolOutput with success results → stream resumes
  - On reject with feedback: call addToolOutput with feedback → stream resumes, state → building
  - On complete rejection: call addToolOutput with rejection → stream resumes

### 6.11 Agent Chat UI
- [ ] Create `components/features/agent/AgentChatPanel.tsx`:
  - Chat message list (user messages + AI responses)
  - Input field for user prompts
  - Submit sends to AI with streaming enabled
  - Display loading state during AI response
  - Handle tool calls (read tools execute immediately, proposal tools buffer)
- [ ] Create `components/features/agent/AgentInput.tsx` - input field component

### 6.12 Error Recovery & Iterative Correction
- [ ] Implement auto-retry for transient errors (DB_LOCKED)
- [ ] Implement auto-correction for logic errors (FOREIGN_KEY_VIOLATION):
  - AI analyzes error from execution_failed result
  - AI modifies keyed buffer (upsert fix)
  - AI re-calls confirmChangeSet
  - User must re-approve modified changeset
- [ ] Handle optimistic locking failures (stale data conflicts)

**Done When:**
- AI can read current categories/members/transactions
- AI can propose transaction creates/updates/deletes
- Proposals accumulate in keyed buffer (upsert semantics work)
- AI can correct proposals via re-proposing same key
- AI can remove proposals with DISCARD action
- Review widget displays all change requests with before/after
- User can approve → changes execute atomically
- User can reject with feedback → AI corrects and re-submits
- User can reject completely → AI starts fresh
- Amounts convert correctly (AI speaks decimals, DB stores cents)
- Balance updates after changeset execution
- Errors feed back to AI for auto-correction
- Stream pauses during review, resumes after user decision

**Testing Approach:**
- **Type:** Complex end-to-end workflow testing
- **Method:** AI conversation scenarios (requires OpenAI API key)
- **Tests:**
  - **Basic Proposal:** "Add £42 groceries" → verify review widget shows create operation, approve → verify transaction created
  - **Multi-Operation:** "Add £42 groceries and £15 transport" → verify both in keyed buffer, approve → verify both created atomically
  - **Upsert Correction:** AI proposes £42, user says "should be £45", AI re-proposes → verify buffer updated (not duplicated)
  - **Discard:** AI proposes 2 transactions, user says "remove second one" → verify AI uses DISCARD action
  - **Iterative Refinement:** Reject with feedback "change amount to £45" → verify state returns to building, AI corrects, re-submits
  - **Complete Rejection:** Reject without feedback → verify state marked rejected, AI starts fresh
  - **Amount Conversion:** AI proposes "42.50" → verify stored as 4200 in DB, review widget displays "£42.50"
  - **Atomic Execution:** Create changeset with 3 operations, force 2nd to fail → verify rollback (none applied)
  - **Error Recovery:** Propose transaction with invalid categoryId → verify error fed to AI, AI auto-corrects
  - **Stream Pause:** Verify AI stream pauses after confirmChangeSet, resumes after approve/reject
